# Kanban

The project board (`/w/:slug/projects/:key`) and the My Tasks board view are
built on the `@reui/c-kanban-1` primitives, which wrap **dnd-kit**
(`@dnd-kit/core` + `@dnd-kit/sortable`). This file is the reasoning behind the
implementation — the parts that are not obvious from reading the code, and the
traps that cost time the first time round.

Reinstall the vendored component with:

```
npx shadcn@latest add @reui/c-kanban-1 -o -y
```

`-o -y` matters: this environment has no stdin, and the interactive overwrite
prompt hangs forever. Use `--dry-run` first to see what it would touch — it
only ever rewrites existing shadcn primitives with a no-op `"use client"`
directive, and skips them as identical.

## 2. Ranking is fractional indexing, not integers

Ordering is a `text` column holding a lexicographically-sortable key
(`fractional-indexing`'s `generateKeyBetween`, a LexoRank equivalent). Sorting
is `a.rank.localeCompare(b.rank)` (`byRank`, exported from `queries/tasks.ts`).
Inserting between two cards never touches any other row — that is the entire
point, and it is why a drag is a single `UPDATE` rather than a renumbering of
the column.

**The sharp edge:**

```
generateKeyBetween(afterRank, beforeRank)  // throws unless afterRank < beforeRank
```

Tasks created but never reordered all share the *same* default rank, so equal
neighbours are the common case in a fresh project, not an edge case. An
unguarded call 500s the request.

This is handled in **two** places, deliberately:

- **Server** (`reorderTask`) catches the throw and retries as
  `generateKeyBetween(afterRank, null)` — "append after the tied run". The
  endpoint refuses to 500 on a drag it can resolve itself. `task-crud.spec.ts`
  covers this with a tied-neighbour reorder.
- **Clients** (`BoardPage.onBoardCommit`, `BacklogPage.onDragEnd`) drop
  `beforeTaskId` to `null` when the two neighbouring ranks are not strictly
  increasing. This is not redundancy for its own sake: it makes the client's
  *optimistic* rank identical to the one the server will persist, so the card
  does not visibly re-settle after the response.

## 3. `reorderTask` does more than move a card

`PATCH /api/workspaces/:slug/projects/:key/tasks/:taskKey/reorder`
Body: `{ status?, afterTaskId?, beforeTaskId? }` (all optional, `.strict()`).
Role: `project_admin | developer`.

In order:

1. Read the neighbours' ranks, compute `newRank` (with the tie fallback above).
2. In a transaction:
   - if `status` changed, run it through `completedAtFor(oldStatus, newStatus, now)`
     so **dragging into/out of Done sets `completedAt`** exactly like editing
     the status field does. Easy to forget, and quietly corrupts cycle-time
     analytics when missed;
   - `UPDATE tasks SET rank, status?, completedAt?, updatedAt`;
   - `logAuditAction('task.rank_changed')` if the rank moved;
   - `logAuditAction('task.status_changed')` **and**
     `recordStatusTransition(tx, {...})` if the status moved — the transitions
     table is what `AnalyticsPage` reads for cycle time and throughput;
   - emit `task_updated` to `project:${projectId}` over socket.io.
3. Outside the transaction: notify assignee and reporter (skipping the actor)
   with a `task_status_changed` notification, only when the status changed.

The audit + transition + notification block is the expensive part to
rediscover. The rank arithmetic is five lines.

## 4. `useMoveTaskMutation` computes the rank twice on purpose

The naive optimistic update patches `status` only. That leaves the card
holding its *old* rank, so it sorts to the wrong slot among its new column's
siblings, then jumps a second time when the PATCH returns the real rank. Two
visible snaps per drag — reads as lag even when the request is fast.

So its `onMutate` computes the same key the server will, from the same
neighbours the caller already resolved, with the same library, and writes it
straight into the TanStack Query cache for `['tasks', slug, key]` — then
`onSuccess` **adopts the server's rank**, overwriting the guess. Skipping that
adoption means the next drag computes neighbours from a stale value and
positions drift over a session.

`onMutate` returns a snapshot of the pre-mutation cache (`{ previous }`), and
`onError` restores it with `setQueryData`. That self-healing revert is why
`BoardPage` needs *no* revert logic of its own: the cache goes back to what it
was, `useTasksQuery` re-renders with it, and the page's `filtered` memo and
`columns`-sync effect pick it up automatically — the same shape the old
Zustand-store version had, just backed by the query cache instead of
`set({ tasks: previous })`.

`MyTasksPage` is the opposite case — it owns its `tasks` locally, outside the
cache, so it *does* hand-write a revert in `onBoardCommit`'s catch. Worth
keeping that asymmetry in mind before moving board state around.

## 5. Component contracts worth knowing

Learned from reading `kanban.tsx`, not from the docs:

- **`value` is genuinely owned by the component mid-drag.** It must be React
  state, re-derived from the fetched tasks by an effect, not a `useMemo`. The
  in-flight reorder lives only in that state until commit. Both boards carry a
  `react-hooks/set-state-in-effect` disable comment explaining exactly this.

- **`KanbanColumn` is itself sortable** via `useSortable` — columns can be
  dragged past each other — *unless nothing inside it renders a
  `KanbanColumnHandle`*. Omitting the handle is what pins the status columns
  to a fixed Todo → In Progress → In Review → Done order. Not documented
  anywhere; only visible in the source.

- **Drag listeners are exposed only through `KanbanItemHandle`**, never
  through `KanbanItem`. To make a whole card draggable, the entire card must
  be wrapped in `KanbanItemHandle`.

- **Click-to-open still works on a full-card handle** because the root's
  sensors use dnd-kit distance-based activation
  (`activationConstraint: { distance: N }`) — a stationary click never starts
  a drag, so `onClick` fires normally.

- **`onValueCommit` already guards itself.** Its internal `commitChange` only
  fires when `overContainer !== origin.container || overIndex !== origin.index`
  (items) or the index actually changed (columns). A consumer-side "did
  anything really change?" guard is dead code — don't add one.

- **`KanbanCommitMeta<T>` hands back everything needed** — never re-derive the
  moved item from the raw `DragEndEvent`:

  | field | use |
  | --- | --- |
  | `kind` | `'item'` \| `'column'` — bail early on `'column'` |
  | `activeContainer` / `activeIndex` | index into `meta.previousValue` → the item as it *was* |
  | `overContainer` / `overIndex` | index into the committed `value` → where it *landed* |
  | `previousValue` | the pre-drag grouping, for hand-written reverts |
  | `event` | the raw dnd-kit event, rarely needed |

- **Keyboard drag does not work through a full-card handle.** `KanbanItem`
  spreads dnd-kit's `attributes` (which carry `tabIndex`/`role`), while
  `KanbanItemHandle` spreads `listeners` (which carry `onKeyDown`) — two
  different elements. The focusable one has no key handler and the one with
  the key handler is not focusable, so the keyboard sensor never fires. Cards
  therefore expose the **title as a real `<Link>`** (`KanbanTaskCard`'s `href`
  prop): keyboard users Tab to it and press Enter to open the task, and
  everyone gets middle-click and open-in-new-tab for free. Reordering by
  keyboard is still unavailable on the board — the Backlog, which uses plain
  dnd-kit with a real `<button>` grip, is the accessible reordering surface.

## 6. Card styling

Both boards render one shared `KanbanTaskCard`, built on the `Card` /
`CardContent` shell `c-kanban-1` actually ships — *not* `TaskCardBody`'s plain
div with a dot-and-text priority. Reusing the drag engine while keeping the old
card look does not count as using the component.

The priority pill uses `@/components/ui/badge` with `variant="secondary"` as a
base, then overrides the background/text colour per level via `PRIORITY_CHIP`
(`KanbanTaskCard.tsx`) — solid `bg-priority-*` + `text-white`, built on
DevSync's own frozen `--priority-*` tokens (`index.css`), not reui's
destructive/warning/primary semantic palette. That keeps all four priority
levels (critical/high/medium/low) visually distinct instead of collapsing onto
three generic colours. Solid background rather than a tinted one — a tint
reads as dull on a dark card; reui's own solid badge variants
(`bg-destructive text-white`, etc.) use the same pattern, and
`--priority-critical` is in fact nearly identical to `--destructive`. No
explicit border is added or needed — `Badge`'s base class already sets
`border-transparent`. `c-kanban-1.tsx`'s own demo badges use plain
`variant="secondary"` (no per-priority colour) so the reference file stays a
minimal example rather than duplicating `PRIORITY_CHIP`.

Card contents are deliberately minimal — title, priority, assignee, due date,
nothing else. Task key, issue type, story points, linked commits and
everything besides live on the task detail page; a board is for scanning
status at a glance, and every extra chip is something a reader has to
visually filter out to find those four things. Layout: title (`line-clamp-2`,
a `<Link>` when `href` is given) + priority badge on the top row; assignee
avatar **and name** (not avatar alone — a name reads at a glance without a
hover) and a due-date chip (turns `text-destructive` when overdue and not
done) on the second row, the date pushed right with `ml-auto`.

`TaskCardBody` stays as it is for the list-shaped surfaces (My Tasks' list
view) that were never a kanban card. **Do not merge the two.**

### Nesting rules

- `KanbanItem` and `KanbanColumn` render `<div>` by default, so nesting a
  `<Link>` inside them is fine.
- A nested interactive element inside a full-card handle needs
  `onClick={(e) => e.stopPropagation()}`, or it triggers the card's handler
  too — this is what the task-key link and the My Tasks project-name link do.
- Where a primitive defaults to `<button>` and must contain a real button, use
  Radix `asChild` to swap it for a `<div>` (the pattern the Epics tree uses) —
  HTML forbids interactive-inside-interactive.

## 7. The Backlog is not this component

`BacklogPage` uses plain dnd-kit (`DndContext` + `SortableContext` +
`verticalListSortingStrategy`, `PointerSensor` at `distance: 6`, plus
`KeyboardSensor` with `sortableKeyboardCoordinates`) and a `GripVerticalIcon`
button as the handle. It is a single sortable list, not a board, and it hits
the same `moveTask` / `/reorder` path with `status` unchanged.

Its one distinct idea: neighbours are computed from the *filtered, visible*
list, not the full backlog — the drop target the user actually saw.

## 9. The "Maximum update depth exceeded" crash — what was fixed and what wasn't fully explained

A real board (dozens of tasks, cards of varying height — due-date chips,
different title lengths, assignee avatars) crashed the whole route behind
`ErrorBoundary` after a handful of fast, successive drags, always inside
`DndContext`'s own `measureRect`. A freshly-seeded project with uniform,
bare cards could **not** reproduce it even after 40+ rapid drags — only real
data with varying card heights did, and even then only ~40–50% of the time.
That data-dependence and non-determinism make this one to read carefully
before assuming a future report is "the same bug" or "already fixed".

Two real things were found and fixed:

- **`getItemValue` and `onValueCommit` must be stable identities.** Both sit
  in the dependency arrays of several of *this file's own* internal
  `useCallback`s (`commitChange`, `handleDragStart`, `handleDragOver`,
  `handleDragEnd` — grep for them). `BoardPage` and `MyTasksPage` were both
  passing a fresh `(t) => t.taskId` arrow and an unmemoized `onBoardCommit`
  on every render, silently rebuilding dnd-kit's own drag handlers on every
  parent re-render. Fixed via `queries/tasks.ts`'s exported `getTaskId` and
  wrapping both pages' `onBoardCommit` in `useCallback`. This is a correct,
  worthwhile fix on its own merits — but **measured A/B testing (multiple
  5-run batches against the real board) showed no significant change in the
  crash rate from this fix alone.** It was not the cause of this particular
  crash; it is a real latent bug this investigation happened to surface.
- **`MEASURING_CONFIG` used `MeasuringStrategy.Always`**, which keeps
  re-measuring every droppable continuously, not just during a drag —
  dnd-kit's own more conservative option, `WhileDragging`, only measures
  while a drag is in flight. Switched to `WhileDragging` (the one deliberate
  hand-edit in this vendored file — see the table in §1). This also did not
  move the measured crash rate on its own in isolated A/B testing.

Neither change was individually shown to fix it via controlled A/B (each was
tested alone against the same real project, 5+ runs per side, no significant
rate difference). Combined, together with a full reset of the demo data's
row order, **21 consecutive attempts (an 8-attempt full run, a 40-drag rapid
stress run, and a final 5-run batch) produced zero crashes**, versus a
~40–50% crash rate on the same drag sequence before either change. That is
suggestive, not proof — the crash was never bisected to a single, provably
sufficient cause, and it may depend on the specific content of specific
tasks (title length, presence of a due date/assignee, or something not yet
identified) in a way this investigation did not fully isolate. If it
resurfaces, `tasks/kanban-drag.spec.ts`'s rapid-drag test is the regression
guard, but note it did **not** reliably reproduce the original bug even
against the reverted code — the crash's window is narrower than that test
currently hits, most likely because its seeded tasks are bare/uniform rather
than the varied-height real data the bug needed. A future investigation
should seed varied card content (long titles, due dates, assignees) rather
than trust that test alone to prove a fix.
